## 一、实验过程

### （一）优化Pass序列预测的实现

1. 本次实验基于已有的LLM辅助优化框架 `PassSequencePredict.cpp`，对Pass序列预测Agent进行了多项增强。原有的实现采用单次LLM调用，将LLVM IR文本和Pass描述发送给大模型，由大模型返回一个Pass执行序列，然后按序执行。这种方式虽然简单，但存在两个问题：一是LLM的推理过程被丢弃，无法了解其对序列编排的思考；二是缺少优化前后的IR变化统计，无法量化优化效果。

2. 针对可解释性不足的问题，对响应处理流程进行了重构。原有的handler链直接将 `extract_text_from_xml("sequence")` 加入处理链，只提取最终序列而丢弃了推理过程。重构后改为两阶段处理：分别调用 `extract_xml_tag` 提取 `<reasoning>` 和 `<sequence>` 标签的内容，并将两者都输出到stderr日志。这样既保留了LLM对Pass编排的推理分析，也将其决策过程完整记录下来，便于后续分析和调试。`PassSequencePredict.cpp` 中的相关代码如下：

```cpp
// 第二步：从清理后的 XML 中分别提取 reasoning 和 sequence
std::string reasoning =
  llm.attr("extract_xml_tag")(cleanResponse, "reasoning")
    .cast<std::string>();
std::string sequence =
  llm.attr("extract_xml_tag")(cleanResponse, "sequence")
    .cast<std::string>();

// 输出 LLM 的推理过程到日志，提供可解释性
llvm::errs() << "\n========================================\n";
llvm::errs() << "LLM Pass 序列预测分析\n";
llvm::errs() << "========================================\n";
llvm::errs() << reasoning << "\n";
llvm::errs() << "----------------------------------------\n";
llvm::errs() << "预测序列: " << sequence << "\n";
llvm::errs() << "========================================\n\n";
```

3. 针对量化评估不足的问题，在Pass序列执行前后增加了IR指令数统计。具体做法是遍历Module中所有Function的所有BasicBlock，累加指令数量，在Pass执行前后分别统计并输出差值。这为评估优化效果提供了一个直观的静态指标。`PassSequencePredict.cpp` 中的相关代码如下：

```cpp
// 统计执行前的 IR 指令数
unsigned beforeCount = 0;
for (auto& func : mod) {
  for (auto& bb : func) {
    beforeCount += bb.size();
  }
}
// ... 执行 Pass 序列 ...
// 统计执行后的 IR 指令数
unsigned afterCount = 0;
for (auto& func : mod) {
  for (auto& bb : func) {
    afterCount += bb.size();
  }
}
llvm::errs() << "IR 指令数: " << beforeCount << " -> " << afterCount
             << " (减少 " << (beforeCount - afterCount) << ")\n";
```

4. 在Prompt工程方面，针对LLM响应格式不稳定导致XML解析崩溃的问题，从根源上进行了修复。在用户Prompt模板中，将C++源码和LLVM IR的内容用 `<![CDATA[...]]>` 包裹，避免源码中的 `&`、`<`、`>` 等特殊字符破坏XML结构。同时强化了系统Prompt的输出约束，明确禁止markdown代码块包裹、要求特殊字符转义、列出常见的错误格式并给出反例。关键修改的模板文件如下：

- `PassSummaryUserPrTpl.xml` — 用CDATA包裹hpp和cpp内容
- `PassSeqPredUserPrTpl.xml` — 用CDATA包裹IR内容
- `PassSeqPredSysPrTpl.xml` — 增加输出格式约束和错误示例

同时在 `__init__.py` 中对 `extract_text_from_xml` 函数增加了正则fallback机制：当XML解析失败时，直接用正则表达式匹配标签内容，避免因LLM输出格式问题导致整个程序崩溃。此外，在 `chat` 方法中增加了handler失败时的调试日志输出，将响应的前800个字符打印到stderr，便于排查问题。


### （二）实现代码优化助手

1. 在Pass序列优化完成后，用户往往希望了解IR是否还有进一步优化的空间，以及还可以使用哪些Pass继续优化。为此，实现了独立的**代码开发助手（CodeAdvisor）**，作为一个LLM Pass在优化序列之后运行，对优化后的IR进行分析并给出针对性建议。

2. CodeAdvisor的设计思路是：将已有的Pass描述（复用PassSequencePredict生成的摘要缓存文件）和优化后的IR一起发送给LLM，让LLM结合每个Pass的能力边界，分析IR中仍然存在的优化机会，并给出具体的优化建议。作为一个独立的Pass，它不修改IR，只输出分析结果，对后续编译过程无影响。头文件定义在 `CodeAdvisor.hpp`，实现文件在 `CodeAdvisor.cpp`。核心流程如下：

```cpp
// 收集所有 Pass 的摘要（复用已有的缓存文件）
std::string passSummary;
for (auto& passInfo : mPassesInfo) {
  if (Fs::exists(passInfo.mSummaryPath)) {
    passSummary.append(read_file(passInfo.mSummaryPath));
  }
}
// 将优化后的 IR 序列化为字符串
std::string optimizedIR;
llvm::raw_string_ostream os(optimizedIR);
mod.print(os, nullptr, false, true);
// 读取提示词模板，格式化后发送给 LLM
std::string systemPrompt = read_file(TASK4_DIR "/llm/prompts/AdvisorSysPrTpl.xml");
auto userPrompt = Py::str(read_file(TASK4_DIR "/llm/prompts/AdvisorUserPrTpl.xml"))
    .attr("format")("passes"_a = passSummary, "ir"_a = optimizedIR)
    .cast<std::string>();
```

3. CodeAdvisor使用独立的Prompt模板，系统提示词 `AdvisorSysPrTpl.xml` 要求LLM关注七个方面的优化机会：冗余计算、循环不变量、未展开循环、可内联函数、死代码/死存储、强度削减、代数恒等式。用户提示词 `AdvisorUserPrTpl.xml` 同样使用CDATA包裹IR内容，确保XML格式正确。LLM的响应包含 `<assessment>`（整体评估）和 `<suggestions>`（优化建议列表）两个部分，两者均使用 `extract_xml_tag` 提取纯文本内容，输出到日志。日志输出格式如下：

```log
========================================
代码开发助手 — 优化建议
========================================
整体评估: 当前 IR 已经历了常量折叠、强度削减、公共子表达式消除（仅限二元运算及比较）、死代码消除、LICM（仅限部分指令）、循环展开（因子 2）等 Pass 的处理。但仍有较多优化机会未被利用 ......
----------------------------------------
优化建议:
1. 问题：在 `fft` 函数的 `while.body27` 中，存在重复调用 `%call36 = call i32 @multiply(i32 %wn.0, i32 %13)` ......
2. 问题：在 `main` 最后的 `while.cond21` 循环中 ......
......
========================================
```

4. CodeAdvisor在 `main.cpp` 中注册为LLM优化管道中的最后一个Pass，在PassSequencePredict执行完毕后运行。它接收与PassSequencePredict相同的Pass列表配置，但只使用其中的摘要缓存路径，不执行实际的Pass。


### （三）构造专属测试集

原有的两个LLM测例（`mm.sysu.c`和`fft.sysu.c`）是矩阵乘法和快速傅里叶变换，它们虽然计算量大，但LLM预测的Pass序列与默认固定序列的差异不够显著，无法充分体现LLM在Pass编排上的优势。因此，根据各个Pass的特点和交互依赖关系，设计了两个新的测试用例，每个用例都针对特定的Pass顺序敏感点。

1. **chained-opt.sysu.c**：针对"CP/CF在LICM之前"和"Unroll后需再次CSE"两个关键优化链。该测例包含三重循环嵌套，内层有大量重复计算（如 `aik * bkj` 重复三次）、代数恒等式（`t1*1`、`t2+0`）和循环不变量。默认的固定顺序（LICM→Unroll→CP→CF→CSE→DCE）中，LICM在CP/CF之前，无法识别经过常量折叠才能成为不变量的表达式；Unroll后没有再次CSE，展开产生的冗余代码残留。LLM可以从IR特征中识别这些问题，将CP/CF放在LICM之前，并在Unroll后安排额外的CSE/DCE轮次。

2. **inline-prop.sysu.c**：针对"Inliner→Mem2Reg→CP/CF→LICM"的优化链和DSE的时机。该测例包含多个被循环调用的辅助函数（`multiply`、`add`、`compute_val`），这些函数传递常量参数（如 `compute_val(pos, 1000, 2, 100)`），内联后需要Mem2Reg消除新产生的alloca/load/store，然后CP/CF将常量折叠为 `pos+2100`。默认顺序中LICM在CP/CF之前，折叠后的常量无法被识别为循环不变量；DSE不在最后，内联后产生的冗余store不会被清除。此外，代码中故意放置了连续写入相同位置的冗余store（`a[pos]=val; a[pos]=val;`）来测试DSE的效果。

预期收益：消除函数调用开销，促进跨函数优化（如常量传播、死代码消除），尤其是将 mm 与 main 的循环融合。

### 总结回顾

1.你在实验过程中，有发现什么技巧或心得吗？

- Prompt工程是LLM辅助编译优化的关键。通过CDATA包裹IR内容、明确输出格式约束、提供错误示例，可以显著提升LLM响应的稳定性和可解析性。在实验过程中，最初因LLM输出的XML格式不合法（如`<reasoning>`中包含未转义的`&`、使用markdown代码块包裹等）导致解析崩溃，在AI工具的帮助下，修改提示词即解决了这一问题。

- 如果运行出错可能是LLM的响应token被截断了，调整模型调用的 `max_tokens` 参数可以解决这个问题。

- 使用LLM来生成特定效果的测例是个不错的选择。通过向LLM描述需要测试的Pass顺序敏感点和优化机会，LLM能够根据这些要求生成具有针对性的测试用例，大幅节省了开发时间。

2.你在此次实验中遇到的最难问题和相应解决办法是什么？

- 有个小但隐蔽的问题是输出token截断导致运行出错，这个问题很难从日志中找到，AI工具也无法定位问题，最终在API提供商的统计页面上发现输出token数达到了上限，才定位原因，调整 `max_tokens` 参数后问题得到解决。

- 另一个问题是CodeAdvisor的suggestions标签输出为空。原因是`node.text`只能获取标签的直接文本内容，而`<suggestions>`包含子标签（`<suggestion>`等），其`node.text`为空。解决方案是简化Prompt，将suggestions改为纯文本标签，避免使用嵌套子标签。这样也能提高输出的稳定性
